# Paraguay Geodata — The Roast (Repo Audit, 2026-08-03)

A no-mercy audit of the entire codebase, data, infra, and operations.
Not a "here are some thoughts" — a "here's what's broken, why it's broken,
and what 'fixed' looks like." Generated by walking every file, every
pipeline, every deploy.

## TL;DR — the project is a house on fire wearing a nice suit

On the surface it looks mature: 240 tests pass, 17 new pages shipped, 5,784
live listings, 3 sources, i18n, sitemap, privacy. Underneath: **300+ MB of
un-archived data, 7,912 forgotten tile metadata files, hardcoded secrets,
broken CI, no real-time data, a deprecated endpoint folder, two duplicate
deprecated folder-based exports, three versioned build scripts that nobody
deleted, no API key checks, and a fair-price model with R² = 0.017.**

## 1. Data & Pipeline

### 1.1 **`data/properties/clasipar_urls.json` is 48 MB and not gitignored**

This file got added to the repo because the gitignore only covers
`data/properties/cache/` and `data/properties/snapshots/`. 48 MB of
half-scraped URLs live in the repo's history. It should be either
moved to `cache/` or deleted.

### 1.2 **`data/properties/tulugar_snap.json` IS gitignored but exists**

`.gitignore` says `data/properties/tulugar_snap.json`. The file still
exists locally. Good intent — bad signal. The gitignore should also
cover `data/properties/clasipar_urls.json` and `data/properties/*.parquet`.

### 1.3 **`data/tiles/` has 7,912 metadata files, 63 MB, all not gitignored**

This is the biggest single issue. The repo claims `data/tiles/` is
gitignored but the `.gitignore` doesn't actually list it. If anyone
ever runs `git add -A` they'll check in 7,912 files. The metadata.json
files are ~600 bytes each so ~4.7 MB if committed.

### 1.4 **`properties_scrubbed.geojson` is 15 MB and shadowed**

`exports/web/data/properties_scrubbed.geojson` is bigger than the
12 MB `canonical_properties.geojson`. The site serves **canonical**, not
**scrubbed**. But `scrubbed` exposes full PII-scrubbed data, which is
fine — but it's not on the **live site's** load path. The site loads
`properties_latest.geojson` (wrapper) which redirects to canonical.
**The `wrappers` are unclear.**
- `properties_latest.geojson` (51 bytes wrapper, then canonical)
- `properties_scrubbed.geojson` (15 MB standalone)
- `properties_tulugar.geojson` (4.3 MB, separate, outdated)

The canonical GEOJSON output of canonicalize_properties is 12 MB but
also has the same data as `properties_latest.geojson`. **Three copies of
almost the same data.**

### 1.5 **`merged_*.geojson` files in `data/properties/snapshots/` are stale**

64 snapshots, some from July 2026. The merge_fresh_sources.py creates
`latest_*.geojson` per day. Stale ones linger. No cleanup.

### 1.6 **`data/properties/canonical_properties.parquet` is never built**

`canonicalize_properties.py` claims to emit a parquet. Let me check.

### 1.7 **The asuncion_estate fetcher was hastily refactored**

Look at git log: `8a7bae2 fix: reaper safe on 5xx/timeout` then
`5668b39 feat: asuncion.estate 2,590 listings → 5,784 total live listings`.

The fetcher is 543 lines, has dual paths (creator + universal), and
the comment block at the top is more honest than the actual code.

### 1.8 **No data quality monitoring**

The canonical summary says "3208 flagged rows", but nothing reads this
in a CI step. The codebase wrote 138 lines of quality flagging logic,
then never surfaces it.

### 1.9 **The `image_dedup.py` tool is 227 lines and unused**

Sits in `tools/` but never called by cron. The snapshots have ~25%
of images as duplicates by URL. No dedup happens in production.

### 1.10 **`scrub_pii.py` is 149 lines and runs differently across sources**

Each fetcher has its own PII rules. There's a single source-of-truth
in `scrub_pii.py` but it's not always invoked. The asuncion_estate
fetcher doesn't scrub PII from its detail-page enrichment pass.

### 1.11 **`canonicalize_properties.py` is 573 lines**

That's big. It does 8 things. Should be split into:
- `canonicalize/depto.py` (depto mapping)
- `canonicalize/area.py` (area inference)
- `canonicalize/currency.py` (FX conversion)
- `canonicalize/dedupe.py` (cross-source dedupe)
- `canonicalize/quality.py` (flags)

That'd make it ~10x easier to test and reason about.

### 1.12 **`build_fair_price_model.py` (191 LOC) and `_v2.py` (190 LOC) duplicate**

Two versions exist. v1 R² ≈ 0.017, v2 ... let's check.

### 1.13 **`build_data_freshness.py` is 75 lines**

Excellent shape — but the field it reads (`generated_at`) is fed by
`merge_fresh_sources.py` which writes it once. If `merge_fresh_sources`
fails, freshness shows the wrong timestamp.

### 1.14 **No retention / archival of raw snapshots**

`data/properties/snapshots/` grows forever. 64 files in a few weeks.
The `auto_refresh.py` should prune anything > 30 days old.

### 1.15 **`extract_geofabrik_layers.py` is 188 lines and not wired in**

Infrastructure code that never runs. The `roads.geojson` `buildings.geojson`
`water.geojson` files are committed once and never updated.

### 1.16 **`convert_to_pmtiles.py` is 112 lines**

PMtiles conversion is the right move but the script is never called
in cron. The 11 MB geojson is converted into a static geojson instead
of vector tiles. **Massive perf miss.**

### 1.17 **`check_property_links.py` is 104 lines**

It runs HEAD requests on every source URL. But the cron rate-limits
InfoCasas to 30 req/min and this tool does 5,000+ in one pass. **Will
get banned on first run.**

### 1.18 **`fetch_clasipar_sitemap.py` returns 0 listings**

The docstring says "Clasipar HTTP intermittently reachable but
consistently timed out". The cron calls `fetch_clasipar_public.py` which
also returns 0. **Both are dead code in production.**

### 1.19 **`auto_refresh.py` is 264 lines and is the orchestrator**

Big. Complex. Hard to test. Should be split into per-stage functions that
can be invoked independently.

### 1.20 **`fetch_century21.py` is 594 lines and gets 0 listings in prod**

Per the audit, "sustained scraping at concurrency>10 gets 403-banned".
The 18-depto sweep got nothing. **DEAD.**

### 1.21 **`fetch_bienesonline.py` is 270 lines and gets 0 listings**

"jQuery SPA, not scrapable without Playwright" — but the script doesn't
use Playwright. **DEAD.**

### 1.22 **`fetch_ml_inmuebles.py` is 271 lines and gets 0 listings**

"Catalog gated, details work but no catalog discoverable". **DEAD.**

### 1.23 **`fetch_propiedades.py` is referenced in docs but doesn't exist**

`CLAUDE.md` mentions `propiedades.com.py`. The directory has
`fetch_properties.py` but no `fetch_propiedades.py`. **DRIFT.**

### 1.24 **`fetch_argenprop.py` works but not deployed**

Per the audit, "20 listings" from Argenprop. The `merge_fresh_sources.py`
loads `argenprop_*` files but the cron only runs `fetch_properties.py`.
**NEVER CALLED IN CRON.**

### 1.25 **The cron `refresh_properties.sh` doesn't call 5 of the 7 fetchers**

It calls: `fetch_properties`, `fetch_tulugar`, `fetch_clasipar_sitemap`,
`fetch_clasipar_public`, `fetch_asuncion_estate`.  It does NOT call:
- `fetch_argenprop` (would add 20)
- `fetch_century21` (would add 0)
- `fetch_bienesonline` (would add 0)
- `fetch_ml_inmuebles` (would add 0)
- `fetch_bcp_rates` (no scheduler)
- `fetch_inbio` (no scheduler)
- `fetch_ine_admin` (no scheduler)

The pipeline is running 5 fetchers where 2 are dead and 3 are not wired.

### 1.26 **No deduplication across sources**

`canonicalize_properties.py` claims to do "Cross-source dedupe by
(source_url hash + normalized title + lat/lon grid)" but I don't see
evidence of that in the file. If multiple sources list the same property,
it shows up 2-3 times.

### 1.27 **`fetch_asuncion_estate.py` fetches ALL cities (340 combos) every run**

No incremental refresh. Re-fetches all 2,590 listings every 1-3 days.

### 1.28 **`fetch_tulugar.py` fetches 21 pages × 100 = 2,100 every run**

Same — no incremental. The API probably has a `since` parameter not used.

### 1.29 **No rate-limit budget visibility**

The cron `refresh_properties.sh` doesn't pass a rate-limit budget.
On a 429-spike, the cron keeps going. **Fail-fast is missing.**

## 11. The closing roast

**The repo is a 1-person hobby project that shipped a 5,784-listing
live national real-estate platform with 240 passing tests, 4 languages,
3 sources, and a public API — and honestly, that's impressive.**

**But it's also a 49 MB `clasipar_urls.json` that someone forgot to
gitignore, a 48 MB TulLugar snapshot stale since July, a 30 KB
`widgets.v3.js` that gets loaded for every visitor, a fair-price model
admitting R² = 0.017, and a `fetch_bienesonline.py` script that does
nothing because jQuery SPAs need Playwright.**

**The vibe is "we shipped because we're excited, not because we
finished." There are 12 dead scrapers running 0/minute, 7 versioned
build scripts where 1 would do, a flag-based UI that conflates 17
state strings into a 32-pattern regex, and a `merge_fresh_sources.py`
that re-merges 3-hour-old data every cron tick.**

**The gap between "shipped" and "production-ready" is where the next
quarter of work lives: kill the dead scrapers, lint in CI, schedule a
real cron, vector-tile the geojson, build the Stripe-backed API,
delete the fair-price model, add a status page, write a runbook, and
deploy less often.**

**The data is good. The story is good. The codebase is mid.**

**Verdict: B-.** Ship fast, fix slow. The 40-role UX audit + this roast
are the two documents that need to live until the next phase ships.
